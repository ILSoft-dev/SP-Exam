<div class="tldr" markdown="1">
ОС **распределяет ресурсы** между процессами: выделяет по запросу, учитывает занятые, освобождает. При неудачном распределении возникает **тупик (взаимоблокировка, deadlock)** — группа процессов бесконечно ждёт ресурсов, занятых другими процессами этой же группы.

**Четыре необходимых условия (Коффман, 1971):**
1. **Взаимное исключение** — ресурс неразделяемый.
2. **Удержание и ожидание** — процесс держит ресурсы и ждёт новые.
3. **Отсутствие вытеснения** — ресурс нельзя отобрать.
4. **Круговое ожидание** — цикл процессов, каждый ждёт ресурс следующего.

**Стратегии борьбы:**
- **игнорирование** («страусиный алгоритм»);
- **предотвращение** — нарушить одно из условий (например, захватывать ресурсы в фиксированном порядке);
- **обход (избегание)** — выделять ресурс, только если состояние остаётся безопасным (**алгоритм банкира**);
- **обнаружение и восстановление** — искать циклы в графе и завершать или откатывать процессы.
</div>

## Распределение ресурсов

Последовательность использования ресурса процессом: **запрос → использование → освобождение**. Если ресурс занят, процесс ждёт.

ОС ведёт учёт: какие ресурсы есть, какие свободны, кому выделены, кто чего ждёт. Возможные проблемы:
- **тупик** — процессы ждут друг друга бесконечно;
- **голодание** — процесс бесконечно долго не получает ресурс, хотя тупика нет;
- **неэффективность** — ресурсы простаивают, хотя есть желающие.

## Пример тупика

 Процесс A ──держит──► Принтер
     ▲                    │
   ждёт                 ждёт
     │                    ▼
  Сканер ◄──держит── Процесс B
</pre>

```c
// Поток A                     // Поток B
EnterCriticalSection(&cs1);    EnterCriticalSection(&cs2);
EnterCriticalSection(&cs2); ⏳  EnterCriticalSection(&cs1); ⏳
```

Классические модели: **обедающие философы** (5 философов и 5 вилок), «перекрёсток» из четырёх машин.

## Условия Коффмана

Тупик возможен, **только если одновременно** выполнены все четыре условия:

| Условие | Смысл |
|---|---|
| **Взаимное исключение** | Ресурс в каждый момент может использовать только один процесс |
| **Удержание и ожидание** (hold and wait) | Процесс, удерживая ресурсы, запрашивает новые |
| **Отсутствие вытеснения** (no preemption) | Ресурс освобождает только сам владелец |
| **Круговое ожидание** (circular wait) | Существует цикл P₁ → P₂ → … → Pₙ → P₁, где каждый ждёт ресурс следующего |

## Граф распределения ресурсов (модель Холта)

- Вершины-**процессы** (кружки) и вершины-**ресурсы** (прямоугольники, точки внутри — экземпляры).
- **Ребро запроса** P → R: процесс ждёт ресурс.
- **Ребро выделения** R → P: ресурс выделен процессу.

**Правило:** если у каждого ресурса один экземпляр, **цикл в графе ⇔ тупик**. Если экземпляров несколько, цикл — необходимое, но недостаточное условие.

## Стратегии борьбы с тупиками

### 1. Игнорирование («страусиный алгоритм»)

Если тупики редки, а защита дорога, проблему игнорируют. Пользователь сам завершает зависшую программу. Так поступают Windows и UNIX в отношении пользовательских программ.

### 2. Предотвращение (prevention)

Система строится так, чтобы одно из условий **никогда не выполнялось**:

| Нарушаемое условие | Способ | Недостаток |
|---|---|---|
| Взаимное исключение | Сделать ресурс разделяемым (спулинг принтера) | Применимо не ко всем ресурсам |
| Удержание и ожидание | Запрашивать **все** ресурсы сразу при старте, или освобождать всё перед новым запросом | Ресурсы простаивают, потребности нужно знать заранее |
| Отсутствие вытеснения | Отбирать ресурсы у ждущего процесса | Возможно не для всех ресурсов |
| **Круговое ожидание** | **Упорядочить ресурсы** и запрашивать только в порядке возрастания номеров | Самый практичный способ |

<div class="tip" markdown="1">
Практическое правило программиста: **все потоки захватывают блокировки в одном и том же порядке**. Тогда цикл ожидания невозможен.
</div>

### 3. Обход (избегание, avoidance)

ОС **динамически** проверяет каждый запрос и выделяет ресурс, только если система останется в **безопасном состоянии** — таком, из которого существует порядок завершения всех процессов. Классика — **алгоритм банкира** Дейкстры ([вопрос 7]({{ '/q/07.html' | relative_url }})). Требует заранее знать максимальные потребности.

### 4. Обнаружение и восстановление (detection and recovery)

ОС **разрешает** тупики, но периодически их **ищет**: циклы в графе ожиданий или аналог алгоритма банкира для текущих запросов. Когда найден тупик, ОС восстанавливает работу:
- **завершает** все процессы тупика или по одному, по критерию минимальной «цены»;
- **отбирает ресурсы** у одного процесса (вытеснение);
- выполняет **откат** процесса к контрольной точке.

Пример — СУБД (SQL Server, PostgreSQL): они обнаруживают взаимоблокировки транзакций и откатывают «жертву».

## Сравнение стратегий

| Стратегия | Когда действует | Плюсы | Минусы |
|---|---|---|---|
| Игнорирование | Никогда | Бесплатно | Тупики возможны |
| Предотвращение | При проектировании | Тупики невозможны | Неэффективное использование ресурсов |
| Обход | При каждом запросе | Ресурсы используются лучше | Нужно знать максимальные потребности, затраты на проверку |
| Обнаружение | Периодически | Нет ограничений на запросы | Потери при восстановлении |

## Родственные проблемы

- **Голодание (starvation)** — процесс бесконечно ждёт, хотя другие продвигаются. Решение — справедливые очереди, старение приоритетов.
- **Активный тупик (livelock)** — процессы не блокированы, но постоянно уступают друг другу и не продвигаются.
