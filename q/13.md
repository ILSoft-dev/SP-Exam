<div class="tldr" markdown="1">
**Способы выполнения ввода-вывода:**
- **программный (с опросом)** — процессор сам ждёт готовности устройства;
- **по прерываниям** — процессор занят другой работой, устройство сообщает о готовности прерыванием;
- **DMA (прямой доступ к памяти)** — контроллер DMA передаёт целый блок без процессора, прерывание приходит только в конце.

**Логическая структура подсистемы ввода-вывода** (слои): пользовательский процесс → **независимый от устройств** уровень (имена, буферизация, ошибки, защита) → **драйверы устройств** → **обработчики прерываний** → оборудование.

**Буферизация** согласует скорости и размеры порций: **одинарный**, **двойной**, **кольцевой** буфер, **дисковый кеш**.

**Дисковое планирование** уменьшает время **позиционирования головок**: **FIFO**, **SSTF** (ближайший запрос), **SCAN** (лифт), **C-SCAN**, **LOOK / C-LOOK**. Для SSD важно объединение запросов, а не порядок.
</div>

## Задачи подсистемы ввода-вывода

- **Эффективность** — ввод-вывод намного медленнее процессора, нужно совмещать их работу.
- **Универсальность (независимость от устройств)** — единообразный интерфейс для всех устройств: в UNIX «всё есть файл», в Windows `CreateFile`/`ReadFile` и для файлов, и для портов, и для каналов.
- Согласование скоростей, **буферизация** и **кеширование**.
- **Разделение** устройств между процессами.
- Обработка **ошибок**.
- Поддержка **синхронного** и **асинхронного** ввода-вывода.

## Способы выполнения ввода-вывода

| Способ | Как работает | Процессор |
|---|---|---|
| **Программный (опрос, polling)** | Процессор выдаёт команду и в цикле проверяет регистр состояния | Занят всё время ожидания |
| **По прерываниям** | Процессор выдаёт команду и переключается на другую работу. Устройство генерирует прерывание при готовности | Обрабатывает прерывание на каждое слово или блок |
| **DMA** | Процессор задаёт контроллеру DMA адрес в памяти, счётчик и направление. Контроллер сам передаёт блок и генерирует **одно** прерывание в конце | Свободен, кроме начала и конца операции |

Эволюция: прямое управление → контроллер → прерывания → DMA → **канал / процессор ввода-вывода** (специализированный процессор, выполняет программы ввода-вывода: мейнфреймы IBM).

## Логическая структура

<pre class="diagram">
┌───────────────────────────────┐
│ Пользовательский процесс      │ ReadFile/read, библиотеки
├───────────────────────────────┤
│ Независимое от устройств ПО   │ имена, защита, буферы,
│ (I/O Manager, VFS)            │ кеш, ошибки, блокировки
├───────────────────────────────┤
│ Драйверы устройств            │ команды контроллеру
├───────────────────────────────┤
│ Обработчики прерываний        │ ISR, DPC
├───────────────────────────────┤
│ Оборудование (контроллеры)    │
└───────────────────────────────┘
</pre>

- В **Windows** диспетчер ввода-вывода (**I/O Manager**) создаёт для каждого запроса пакет **IRP** и передаёт его по **стеку драйверов** ([вопрос 38]({{ '/q/38.html' | relative_url }})).
- Устройства бывают **блочные** (диски: адресуемые блоки) и **символьные** (клавиатура, COM-порт: поток байтов).

## Синхронный и асинхронный ввод-вывод

- **Синхронный (блокирующий):** поток ждёт завершения операции. Это просто.
- **Асинхронный (неблокирующий, overlapped):** функция возвращает управление сразу, поток продолжает работу и **позже** узнаёт о завершении.

```c
// Windows: асинхронное чтение
HANDLE h = CreateFile(L"big.dat", GENERIC_READ, 0, NULL,
                      OPEN_EXISTING, FILE_FLAG_OVERLAPPED, NULL);
OVERLAPPED ov = {0};
ov.hEvent = CreateEvent(NULL, TRUE, FALSE, NULL);
ReadFile(h, buf, sizeof buf, NULL, &ov);   // вернётся сразу (ERROR_IO_PENDING)
/* ... полезная работа ... */
DWORD n;
GetOverlappedResult(h, &ov, &n, TRUE);     // дождаться завершения
```

Механизмы уведомления в Windows: событие, **APC-процедура** (`ReadFileEx`), **порты завершения ввода-вывода (IOCP)**. В Linux: `select`/`poll`/`epoll`, `aio`, **io_uring**.

## Буферизация

**Зачем:** согласовать **скорости** устройства и процесса, **размеры** порций данных (байты и блоки), позволить процессу работать параллельно с вводом-выводом, обеспечить **семантику копирования** (данные можно изменять сразу после `write`).

| Схема | Как работает | Эффект |
|---|---|---|
| **Без буфера** | Данные передаются прямо в память процесса | Процесс ждёт. Страница процесса закреплена в памяти |
| **Одинарный буфер** | ОС читает блок в системный буфер, затем копирует процессу. Пока процесс обрабатывает блок, ОС читает следующий (упреждающее чтение) | Совмещение обработки и ввода-вывода |
| **Двойной буфер** | Два буфера: в один пишет устройство, из другого читает процесс, затем они меняются | Непрерывный поток данных |
| **Кольцевой (циклический) буфер** | N буферов по кругу. Это задача «производитель–потребитель» | Сглаживает всплески скорости |
| **Кеш (дисковый)** | Часто используемые блоки хранятся в ОЗУ. **Отложенная запись** и **упреждающее чтение** | Повторный доступ без обращения к диску |

**Кеширование в ОС:** диспетчер кеша Windows, page cache в Linux. Данные сбрасываются на диск функциями `FlushFileBuffers` и `fsync`/`sync`. Флаги `FILE_FLAG_NO_BUFFERING` и `FILE_FLAG_WRITE_THROUGH` в Windows, `O_DIRECT` и `O_SYNC` в Linux.

## Дисковое планирование

Время доступа HDD = **позиционирование (seek)** + **задержка вращения** + передача. Самое дорогое — перемещение головок, поэтому запросы **упорядочивают**.

**Пример:** головка на дорожке **53**, очередь: 98, 183, 37, 122, 14, 124, 65, 67 (дорожки 0–199).

| Алгоритм | Правило | Порядок | Перемещение |
|---|---|---|---|
| **FIFO (FCFS)** | По порядку поступления | 98, 183, 37, 122, 14, 124, 65, 67 | **640** |
| **SSTF** | Ближайший к головке запрос | 65, 67, 37, 14, 98, 122, 124, 183 | **236** |
| **SCAN («лифт»)** | Движение в одну сторону до края, затем обратно (движемся к 0) | 37, 14, (0), 65, 67, 98, 122, 124, 183 | **236** |
| **C-SCAN** | Обслуживание только в одну сторону, затем возврат к началу без обслуживания (движемся к 199) | 65, 67, 98, 122, 124, 183, (199 → 0), 14, 37 | **382** (с учётом возврата) |
| **LOOK / C-LOOK** | Как SCAN / C-SCAN, но разворот у последнего запроса, а не у края | LOOK к 0: 37, 14, 65, 67, 98, 122, 124, 183 | **208** |

- **SSTF** может вызывать **голодание** далёких запросов.
- **SCAN / C-SCAN** дают более **равномерное** время ожидания. C-SCAN справедлив к краевым дорожкам.
- Современные ОС: Linux — **mq-deadline**, **BFQ**, **kyber**, **none** (для NVMe). Сами диски переупорядочивают запросы (**NCQ**). Для **SSD** время позиционирования отсутствует, поэтому важнее объединение запросов и параллелизм.
