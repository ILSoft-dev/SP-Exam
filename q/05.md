<div class="tldr" markdown="1">
Процессы и потоки **взаимодействуют**: **конкурируют** за общие ресурсы и **сотрудничают** — обмениваются данными, ждут друг друга. Так как они выполняются асинхронно, при работе с общими данными возникают **гонки (race condition)** — результат зависит от соотношения скоростей.

**Критическая секция (КС)** — участок кода, работающий с разделяемыми данными. **Задача взаимного исключения** — обеспечить, чтобы в КС по одному ресурсу одновременно находился **не более чем один** процесс.

Требования к решению: **взаимное исключение**, **прогресс** (процесс вне КС не мешает другим), **ограниченное ожидание** (нет голодания), **никаких предположений о скоростях** и числе процессоров.

Решения:
- **программные:** алгоритмы **Деккера** и **Петерсона**;
- **аппаратные:** **запрет прерываний**, атомарные команды **TSL/XCHG/CAS** (спин-блокировки);
- **системные:** **семафоры** (P/V), **мьютексы**, **мониторы**, события. Они не требуют активного ожидания.

Классическая задача — **«производители–потребители»**, решается тремя семафорами: `mutex = 1`, `empty = N`, `full = 0`.
</div>

## Виды взаимодействия процессов

- **Конкуренция** за ресурсы: процессы не знают друг о друге, но используют общий принтер, файл или переменную. Нужно **взаимное исключение**.
- **Сотрудничество через разделяемые данные**: общая память, файл. Нужны взаимное исключение и согласование.
- **Сотрудничество через обмен сообщениями**: каналы, очереди, сокеты. Нужна **синхронизация** — получатель ждёт сообщение.

Проблемы взаимодействия: **гонки**, **тупики** ([вопрос 6]({{ '/q/06.html' | relative_url }})), **голодание**.

## Гонки: пример

```c
int balance = 1000;        // общий счёт

void withdraw(int sum) {   // выполняют два потока
    int b = balance;       // 1. прочитать
    b = b - sum;           // 2. вычислить
    balance = b;           // 3. записать
}
```

Два потока снимают по 300. Если поток A прервётся после шага 1, а поток B выполнит все три шага, то A запишет **700** поверх 700, и итог будет 700 вместо 400. Даже `count++` не атомарна: это три машинные команды.

## Требования к решению (Дейкстра)

1. **Взаимное исключение** — в КС не более одного процесса.
2. **Прогресс** — если КС свободна, то вход в неё не может откладываться бесконечно. Решение о входе принимают только претенденты.
3. **Ограниченное ожидание** — процесс, запросивший вход, войдёт за конечное время.
4. **Независимость от скоростей** — никаких предположений об относительной скорости процессов и числе процессоров.

## Программные решения

### Неверные попытки

- **Флаг занятости** `while (busy); busy = 1;` — проверка и установка не атомарны, оба процесса могут войти.
- **Строгое чередование** `while (turn != i);` — взаимное исключение есть, но нарушен **прогресс**: процесс не может войти дважды подряд.

### Алгоритм Петерсона (для двух процессов)

```c
volatile int  turn;
volatile bool want[2] = { false, false };

void enter(int i) {
    int j = 1 - i;
    want[i] = true;           // хочу войти
    turn = j;                 // уступаю очередь
    while (want[j] && turn == j)
        ;                     // активное ожидание
}
void leave(int i) { want[i] = false; }
```

Если оба хотят войти, входит тот, кто записал `turn` первым: второй своей записью уступил ему. Алгоритм удовлетворяет всем четырём требованиям. **Алгоритм Деккера** (1965) — первое корректное программное решение, сложнее.

Недостатки программных решений: **активное ожидание** (busy waiting) тратит процессор, они работают только для заранее известного числа процессов, а на современных процессорах требуют **барьеров памяти**.

## Аппаратные решения

- **Запрет прерываний** на время КС. Работает только на **одном процессоре** и только в **ядре**: пользовательской программе это давать нельзя.
- **Атомарные команды:** **TSL** (Test-and-Set Lock), **XCHG**, **CMPXCHG** (compare-and-swap). Проверка и установка выполняются неделимо:

```c
#include <stdatomic.h>
atomic_flag lock = ATOMIC_FLAG_INIT;
void enter(void) { while (atomic_flag_test_and_set(&lock)) ; } // спин
void leave(void) { atomic_flag_clear(&lock); }
```

Это **спин-блокировка**. Она эффективна для очень коротких КС на многопроцессорных системах (так работает само ядро ОС).

## Системные решения: семафоры, мьютексы, мониторы

### Семафор Дейкстры

Целочисленная переменная S ≥ 0 с неделимыми операциями:
- **P(S)** (wait, down): если S > 0, то S−−; иначе процесс **блокируется** (без затрат процессора);
- **V(S)** (signal, up, post): S++, и если есть ждущие, один из них пробуждается.

```text
семафор mutex = 1
P(mutex)
  критическая секция
V(mutex)
```

- **Двоичный** семафор (0/1) используется для взаимного исключения.
- **Считающий** семафор (0…N) — для учёта N однотипных ресурсов.
- **Мьютекс** — двоичный семафор с **владельцем**: освободить его может только захвативший поток.

### Монитор

Языковая конструкция (Хоар, Хансен): **общие данные + процедуры**, и в монитор одновременно может войти только один процесс. Для ожидания условий используются **условные переменные** с операциями `wait` и `signal`. Примеры: `lock` и `Monitor` в C#, `synchronized` в Java.

### Средства Windows и POSIX

| | Windows | POSIX / Linux |
|---|---|---|
| Взаимное исключение в процессе | `CRITICAL_SECTION`, `SRWLOCK` | `pthread_mutex_t` |
| Между процессами | `CreateMutex` / `WaitForSingleObject` / `ReleaseMutex` | Именованный семафор `sem_open`, мьютекс в разделяемой памяти |
| Семафор | `CreateSemaphore` / `ReleaseSemaphore` | `sem_wait` / `sem_post` |
| Атомарные операции | `InterlockedIncrement`, `InterlockedCompareExchange` | `__atomic_*`, `<stdatomic.h>` |
| Условные переменные | `CONDITION_VARIABLE` | `pthread_cond_t` |

## Задача «производители–потребители»

Производители кладут элементы в **буфер из N ячеек**, потребители забирают. Нельзя класть в полный буфер, нельзя брать из пустого, работать с буфером одновременно может только один процесс.

```text
семафор mutex = 1   // исключительный доступ к буферу
семафор empty = N   // свободных ячеек
семафор full  = 0   // заполненных ячеек

Производитель:              Потребитель:
  while (true) {              while (true) {
    x = произвести();           P(full);
    P(empty);                   P(mutex);
    P(mutex);                   x = взять();
    положить(x);                V(mutex);
    V(mutex);                   V(empty);
    V(full);                    потребить(x);
  }                           }
```

<div class="warn" markdown="1">
Если поменять местами `P(empty)` и `P(mutex)` у производителя, то при полном буфере он заснёт, удерживая `mutex`. Потребитель не сможет взять элемент, и возникнет **тупик**. Сначала ждём условие, потом захватываем мьютекс.
</div>

### Пример на WinAPI

```c
#define N 10
int buf[N], in = 0, out = 0;
HANDLE hMutex, hEmpty, hFull;

DWORD WINAPI Producer(LPVOID p) {
    for (int i = 0; ; i++) {
        WaitForSingleObject(hEmpty, INFINITE);   // P(empty)
        WaitForSingleObject(hMutex, INFINITE);   // P(mutex)
        buf[in] = i; in = (in + 1) % N;
        ReleaseMutex(hMutex);                    // V(mutex)
        ReleaseSemaphore(hFull, 1, NULL);        // V(full)
    }
}
DWORD WINAPI Consumer(LPVOID p) {
    for (;;) {
        WaitForSingleObject(hFull, INFINITE);
        WaitForSingleObject(hMutex, INFINITE);
        int x = buf[out]; out = (out + 1) % N;
        ReleaseMutex(hMutex);
        ReleaseSemaphore(hEmpty, 1, NULL);
        printf("%d\n", x);
    }
}
int main(void) {
    hMutex = CreateMutex(NULL, FALSE, NULL);
    hEmpty = CreateSemaphore(NULL, N, N, NULL);
    hFull  = CreateSemaphore(NULL, 0, N, NULL);
    HANDLE t[2] = { CreateThread(NULL, 0, Producer, NULL, 0, NULL),
                    CreateThread(NULL, 0, Consumer, NULL, 0, NULL) };
    WaitForMultipleObjects(2, t, TRUE, INFINITE);
}
```
