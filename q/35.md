<div class="tldr" markdown="1">
Обработка прерывания в Windows делится на несколько этапов с понижением IRQL:

1. **ISR (Interrupt Service Routine)** — подпрограмма обработки прерывания драйвера. Выполняется на высоком **DIRQL**, когда устройство выставило прерывание. Делает **минимум**: подтверждает прерывание устройству, сохраняет данные и **ставит в очередь DPC**.
2. **DPC (Deferred Procedure Call)** — отложенный вызов процедуры. Выполняется чуть позже на **DISPATCH_LEVEL**, когда IRQL снизится. Делает **основную** работу обработки (разбор данных, завершение запроса ввода-вывода), пока остальные прерывания уже разрешены.
3. **APC (Asynchronous Procedure Call)** — асинхронный вызов процедуры **в контексте конкретного потока** на **APC_LEVEL** или PASSIVE_LEVEL. Применяется для завершения асинхронного ввода-вывода, доставки в поток результатов и уведомлений.

Такое разделение держит прерывания запрещёнными **минимально**: срочное — в ISR, остальное — в DPC, а то, что должно выполниться в адресном пространстве определённого потока, — в APC.
</div>

## Подпрограмма обработки прерывания (ISR)

- Драйвер регистрирует ISR функцией **`IoConnectInterrupt`** (создаётся **объект прерывания**, KINTERRUPT), связывая её с вектором и DIRQL устройства.
- При прерывании процессор по **IDT** передаёт управление диспетчеру прерываний ядра, тот поднимает IRQL до **DIRQL устройства** и вызывает ISR.
- **ISR выполняется на высоком IRQL**, поэтому все прерывания с меньшим уровнем замаскированы. Она обязана быть **очень короткой**:
  1. проверить, её ли устройство прервало (на общей линии IRQ могут быть несколько устройств);
  2. **подтвердить** прерывание устройству (сбросить сигнал), иначе оно будет повторяться;
  3. сохранить срочные данные из регистров устройства;
  4. **поставить в очередь DPC** (`IoRequestDpc` / `KeInsertQueueDpc`) для основной работы;
  5. вернуть управление.

## Отложенный вызов процедуры (DPC)

**DPC** переносит несрочную часть обработки прерывания на уровень **DISPATCH_LEVEL**, где прерывания устройств уже разрешены.

<pre class="diagram">
 Устройство ──IRQ──► ISR (DIRQL)
                      │ минимум работы
                      │ ставит DPC в очередь
                      ▼
 IRQL снижается ──► DPC (DISPATCH_LEVEL)
                      │ основная обработка:
                      │ разбор данных, IoCompleteRequest
                      ▼
 IRQL → PASSIVE ──► планировщик / APC в потоке
</pre>

- У каждого процессора — своя **очередь DPC**. Когда IRQL падает ниже DISPATCH_LEVEL, ядро выполняет накопленные DPC.
- DPC работает на **DISPATCH_LEVEL**, поэтому для него действуют те же ограничения ([вопрос 34]({{ '/q/34.html' | relative_url }})): **нельзя ждать**, **нельзя** обращаться к подкачиваемой памяти.
- Применение: **завершение обработки прерывания** драйвером, **таймеры ядра** (`KeSetTimer` → DPC), перепланирование (сам планировщик вызывается через DPC — «DPC диспетчеризации»).
- DPC выполняется в **произвольном контексте потока** (того, что был прерван), поэтому не может обращаться к памяти конкретного пользовательского процесса.

## Асинхронный вызов процедуры (APC)

**APC** — функция, которая выполняется **в контексте конкретного потока** асинхронно, когда этот поток к этому готов. В отличие от DPC, APC «привязан» к потоку и его адресному пространству.

### Виды APC

| Вид | IRQL | Контекст | Доставка |
|---|---|---|---|
| **APC режима ядра (специальные)** | APC_LEVEL | Поток в режиме ядра | Как только поток не на APC/выше |
| **APC режима ядра (обычные)** | APC_LEVEL | Поток | Если APC режима ядра не отключены |
| **Пользовательские APC** | PASSIVE_LEVEL | Поток в **пользовательском** режиме | Только когда поток в **тревожном ожидании (alertable wait)** |

### Доставка пользовательского APC

Пользовательский APC выполняется, только когда поток сам входит в **alertable-ожидание**:
```c
// поставить APC другому потоку
QueueUserAPC(ApcProc, hThread, (ULONG_PTR)data);

// поток принимает APC, войдя в alertable-ожидание:
SleepEx(INFINITE, TRUE);                       // TRUE = alertable
WaitForSingleObjectEx(h, INFINITE, TRUE);
// или SignalObjectAndWait, MsgWaitForMultipleObjectsEx с MWMO_ALERTABLE
```

### Применение APC

- **Завершение асинхронного ввода-вывода:** `ReadFileEx`/`WriteFileEx` с процедурой завершения — она вызывается как APC в потоке, инициировавшем операцию.
- **Доставка результатов и уведомлений** в конкретный поток.
- **Завершение и приостановка потоков** (внутренне реализованы через APC режима ядра).
- **Асинхронные вызовы процедур** пользователя (`QueueUserAPC`).

## Сравнение ISR, DPC и APC

| | ISR | DPC | APC |
|---|---|---|---|
| IRQL | DIRQL (высокий) | DISPATCH_LEVEL | APC_LEVEL / PASSIVE_LEVEL |
| Когда | Сразу при прерывании | После ISR, при снижении IRQL | Когда поток готов (для user — alertable) |
| Контекст | Прерванный поток (произвольный) | Произвольный поток | **Конкретный** целевой поток |
| Доступ к памяти процесса | Нет | Нет | **Да** (своё адресное пространство) |
| Можно ждать | Нет | Нет | APC режима ядра — ограниченно; user APC — да |
| Длительность | Минимальная | Короткая | Обычная |
| Назначение | Срочная реакция на устройство | Основная обработка прерывания, таймеры | Работа в контексте потока: завершение ввода-вывода |

## Полный путь обработки (пример: чтение с диска)

1. Поток вызвал `ReadFile` → диспетчер ввода-вывода создал **IRP** и передал драйверу диска. Поток **ждёт**.
2. Диск закончил чтение → **прерывание** → **ISR** (DIRQL): подтвердить прерывание, запросить DPC.
3. **DPC** (DISPATCH_LEVEL): забрать данные, вызвать `IoCompleteRequest(irp)`.
4. Для завершения в контексте вызвавшего потока ставится **APC**: скопировать данные в буфер пользователя, перевести поток в готовность.
5. Поток просыпается на **PASSIVE_LEVEL**, `ReadFile` возвращает управление.
