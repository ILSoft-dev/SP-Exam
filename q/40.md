<div class="tldr" markdown="1">
**Функции Windows API в режиме ядра** реализованы как **системные службы** в `ntoskrnl.exe` (имена `Nt*`/`Zw*`: `NtCreateFile`, `NtReadFile`). Пользовательский вызов через **NTDLL** помещает **номер службы** в регистр и выполняет `syscall`; ядро по номеру находит адрес обработчика в **таблице дескрипторов системных служб — SSDT (System Service Descriptor Table)**.

**SSDT** (`KeServiceDescriptorTable`) — массив адресов системных служб. Диспетчер системных вызовов ядра (`KiSystemService`/`KiSystemCall64`) берёт из него адрес по номеру службы и вызывает.

**Перехват в режиме ядра через SSDT** — замена в этой таблице адреса системной службы на свой обработчик. Тогда **все** вызовы данной функции (от всех процессов) проходят через перехватчик. Исторически так работали антивирусы и мониторы ядра.

**Ограничения на 64-битных Windows:** модификация SSDT (и других структур ядра) **запрещена** механизмом **PatchGuard (Kernel Patch Protection)** — при обнаружении правки система аварийно завершается. Поэтому применяются **поддерживаемые механизмы:** **фильтр-драйверы** (файловые мини-фильтры), **callback-механизмы ядра** (`ObRegisterCallbacks`, `PsSetCreateProcessNotifyRoutine`, `CmRegisterCallback`, WFP). Это легальный путь мониторинга в современных ОС.
</div>

## Системные службы ядра

- Многие функции Win32 — это, по сути, обёртки над **системными службами ядра**. Например, `CreateFile` (kernel32) → `NtCreateFile` (NTDLL) → **системная служба `NtCreateFile`** в ntoskrnl.
- Службы имеют приставки **`Nt`** и **`Zw`** (различаются режимом проверки параметров и предыдущим режимом вызывающего).
- Выполняются в **режиме ядра**, с полным доступом к ресурсам.

## Механизм системного вызова и SSDT

<pre class="diagram">
 Пользовательский режим
  NTDLL: NtCreateFile
    mov eax, N        ; N — номер службы
    syscall           ─── переход в ядро ───
 ─────────────────────────────────────────
 Режим ядра
  Диспетчер системных вызовов (KiSystemCall64)
    адрес = SSDT[N]          ← таблица дескрипторов служб
    проверка параметров
    call адрес  ──► NtCreateFile (ntoskrnl)
    возврат (sysret)
</pre>

- **SSDT (System Service Descriptor Table)**, в ядре — структура **`KeServiceDescriptorTable`**: содержит указатель на **массив адресов** системных служб (`KiServiceTable`), счётчик служб и таблицу числа аргументов.
- **Номер службы** — индекс в этом массиве. У оконно-графических служб (win32k.sys) своя «теневая» таблица **SSDT Shadow**.
- Диспетчер берёт `SSDT[номер]`, проверяет и копирует параметры из пользовательского режима и вызывает службу.

## Перехват функций в режиме ядра через SSDT

**Идея:** драйвер сохраняет оригинальный адрес из SSDT и записывает туда адрес **своей** функции. Теперь ядро при каждом системном вызове этой службы вызывает перехватчик, а он при необходимости вызывает оригинал.

<pre class="diagram">
 До:   SSDT[N] ─► NtCreateFile (оригинал)

 После: SSDT[N] ─► MyNtCreateFile ─► (проверка/лог) ─► оригинал
</pre>

- ➕ **Глобальность:** перехватываются вызовы **всех** процессов на самом низком уровне, где их уже нельзя обойти.
- **Легальные применения (исторически):** антивирусы, HIPS, мониторы доступа к файлам и реестру, песочницы.
- Технические сложности: SSDT в памяти **только для чтения** (нужно снять защиту через MDL или регистр CR0 WP), требуется атомарность и учёт многопоточности.

<div class="warn" markdown="1">
На **64-битных Windows** прямая модификация SSDT, таблицы прерываний (IDT), GDT, образа ядра и других ключевых структур **запрещена** механизмом **PatchGuard (Kernel Patch Protection)**. При обнаружении несанкционированного изменения система немедленно падает с BSOD `CRITICAL_STRUCTURE_CORRUPTION`. Цель — не дать руткитам и даже легальным драйверам опасно «латать» ядро. Поэтому перехват через SSDT в современных ОС **не используется**.
</div>

## Современные поддерживаемые механизмы

Вместо правки SSDT Microsoft предоставляет **документированные точки расширения** ядра — их и применяют антивирусы и мониторы:

| Механизм | Что перехватывает/отслеживает |
|---|---|
| **Файловые мини-фильтры** (Filter Manager, `FltRegisterFilter`) | Операции файловой системы — вместо перехвата `NtCreateFile`. Фильтр встраивается в стек устройств ([вопрос 38]({{ '/q/38.html' | relative_url }})) |
| **`PsSetCreateProcessNotifyRoutineEx`** | Создание и завершение процессов |
| **`PsSetCreateThreadNotifyRoutine`** | Создание и завершение потоков |
| **`PsSetLoadImageNotifyRoutine`** | Загрузку образов (EXE/DLL/драйверов) |
| **`ObRegisterCallbacks`** | Открытие дескрипторов на процессы и потоки (защита процессов) |
| **`CmRegisterCallbackEx`** | Операции с реестром |
| **WFP (Windows Filtering Platform)** | Сетевой трафик |
| **ETW (Event Tracing for Windows)** | Трассировка событий ядра и приложений |

Эти механизмы:
- **совместимы с PatchGuard** (не правят структуры ядра);
- **стабильны** между версиями Windows (документированный интерфейс);
- не ломают систему при ошибке так, как правка SSDT.

## Защита ядра в целом

- **PatchGuard** — контроль целостности структур ядра.
- **DSE (Driver Signature Enforcement)** — только подписанные драйверы в x64.
- **HVCI / VBS** — проверка целостности кода гипервизором.
- **KASLR** — рандомизация адресов ядра.

Эти меры делают неподдерживаемый перехват в ядре невозможным и направляют разработчиков к штатным фильтрам и callback-механизмам.
