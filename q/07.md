<div class="tldr" markdown="1">
**Алгоритм банкира** (Э. Дейкстра, 1965) — алгоритм **обхода (избегания) тупиков**. Аналогия: банкир выдаёт кредиты клиентам так, чтобы в любом случае суметь удовлетворить всех.

Каждый процесс заранее объявляет **максимальную потребность** в ресурсах. При каждом запросе ОС «условно» выделяет ресурсы и проверяет, будет ли новое состояние **безопасным**, то есть существует ли **последовательность**, в которой все процессы смогут получить свой максимум и завершиться. Если да, запрос удовлетворяется. Если нет, процесс **ждёт**, даже если ресурсы свободны.

Структуры данных (n процессов, m типов ресурсов): **Available** (свободно), **Max**, **Allocation** (выделено), **Need = Max − Allocation**.

Проверка безопасности: найти процесс с **Need ≤ Work**, «завершить» его (Work += Allocation), повторять. Если завершились все процессы, состояние безопасное.

➖ Требует знать максимальные потребности и фиксированное число процессов, поэтому в универсальных ОС почти не применяется.
</div>

## Безопасное и опасное состояние

- **Безопасное состояние** — существует **безопасная последовательность** процессов ⟨P₁, P₂, …, Pₙ⟩. Каждый Pᵢ может получить недостающие ресурсы из свободных плюс ресурсов, освобождённых предыдущими процессами, и завершиться.
- **Опасное (небезопасное) состояние** — такой последовательности нет. Это **ещё не тупик**, но тупик **может** наступить, если процессы запросят свой максимум.

┌──────────────────────────────┐
│  Все состояния               │
│  ┌──────────────┐            │
│  │  Безопасные  │  Опасные   │
│  │              │  ┌──────┐  │
│  │              │  │Тупики│  │
│  └──────────────┘  └──────┘  │
└──────────────────────────────┘
</pre>

**Цель алгоритма:** никогда не переходить из безопасного состояния в опасное.

## Структуры данных

Для n процессов и m типов ресурсов:

| Структура | Размер | Смысл |
|---|---|---|
| **Available[m]** | вектор | Сколько ресурсов каждого типа свободно |
| **Max[n][m]** | матрица | Максимальная потребность каждого процесса |
| **Allocation[n][m]** | матрица | Сколько уже выделено |
| **Need[n][m]** | матрица | Сколько ещё может понадобиться: **Need = Max − Allocation** |

## Алгоритм проверки безопасности

```text
Work   := Available
Finish := [false, …, false]

повторять:
    найти i: Finish[i] = false и Need[i] ≤ Work   (покомпонентно)
    если найден:
        Work := Work + Allocation[i]   // процесс завершился и всё вернул
        Finish[i] := true
    иначе выйти

если все Finish[i] = true → состояние БЕЗОПАСНО
иначе → ОПАСНО
```

## Алгоритм обработки запроса Request[i]

1. Если **Request[i] > Need[i]** → ошибка: процесс превысил объявленный максимум.
2. Если **Request[i] > Available** → процесс **ждёт**: ресурсов нет.
3. **Условно выделить:**
   - Available −= Request[i];
   - Allocation[i] += Request[i];
   - Need[i] −= Request[i].
4. Выполнить **проверку безопасности**:
   - безопасно → запрос **удовлетворяется**;
   - опасно → **отменить** условное выделение, процесс **ждёт**.

## Пример 1: один тип ресурса

Всего 12 единиц (например, магнитных лент).

| Процесс | Max | Allocation | Need |
|---|---|---|---|
| P0 | 10 | 5 | 5 |
| P1 | 4 | 2 | 2 |
| P2 | 9 | 2 | 7 |

Available = 12 − 9 = **3**.

Проверка:
- P1: Need 2 ≤ 3 → завершается, Work = 3 + 2 = 5.
- P0: Need 5 ≤ 5 → завершается, Work = 5 + 5 = 10.
- P2: Need 7 ≤ 10 → завершается, Work = 12.

Последовательность **⟨P1, P0, P2⟩** — состояние **безопасное**.

**Запрос:** P2 просит ещё 1. Условно: Available = 2, P2: Allocation 3, Need 6.
- P1: 2 ≤ 2 → Work = 4.
- P0: 5 > 4 ✗. P2: 6 > 4 ✗.

Состояние **опасное**, поэтому запрос P2 **откладывается**, хотя свободная единица есть.

## Пример 2: несколько типов ресурсов

Ресурсы A, B, C, всего (10, 5, 7).

| Процесс | Allocation (A B C) | Max (A B C) | Need (A B C) |
|---|---|---|---|
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

Выделено (7, 2, 5) → **Available = (3, 3, 2)**.

| Шаг | Процесс | Need ≤ Work? | Work после |
|---|---|---|---|
| 1 | P1 | (1,2,2) ≤ (3,3,2) ✓ | (5,3,2) |
| 2 | P3 | (0,1,1) ≤ (5,3,2) ✓ | (7,4,3) |
| 3 | P4 | (4,3,1) ≤ (7,4,3) ✓ | (7,4,5) |
| 4 | P0 | (7,4,3) ≤ (7,4,5) ✓ | (7,5,5) |
| 5 | P2 | (6,0,0) ≤ (7,5,5) ✓ | (10,5,7) |

Безопасная последовательность **⟨P1, P3, P4, P0, P2⟩**.

**Запрос P1 = (1, 0, 2):** (1,0,2) ≤ Need P1 (1,2,2) ✓, (1,0,2) ≤ Available (3,3,2) ✓. Условно: Available = (2,3,0), Allocation P1 = (3,0,2), Need P1 = (0,2,0). Проверка: P1 (0,2,0) ≤ (2,3,0) ✓ → (5,3,2); P3 → (7,4,3); P4 → (7,4,5); P0 → (7,5,5); P2 → (10,5,7). Состояние безопасное — **запрос удовлетворяется**.

**Запрос P0 = (0, 2, 0)** в исходном состоянии: Available станет (3,1,2), Allocation P0 = (0,3,0), Need P0 = (7,2,3). Проверка: P3 (0,1,1) ≤ (3,1,2) ✓ → (5,2,3); P1 (1,2,2) ≤ (5,2,3) ✓ → (7,2,3); P2 (6,0,0) ✓ → (10,2,5); P0 (7,2,3) ✓ → (10,5,5); P4 (4,3,1) ✓ → (10,5,7). Безопасная последовательность ⟨P3, P1, P2, P0, P4⟩ есть, поэтому запрос тоже можно удовлетворить.

## Сложность и применение

- Сложность проверки — **O(m · n²)**.
- **Ограничения:**
  - нужно заранее знать **максимальные потребности**;
  - число процессов и ресурсов должно быть **постоянным**;
  - процессы должны **гарантированно** завершаться и освобождать ресурсы;
  - алгоритм **консервативен**: ресурсы могут простаивать.
- **Применение:** системы с заранее известными задачами (встраиваемые системы, пакетная обработка, управление ресурсами в СУБД и планировщиках заданий), обучение. В универсальных ОС (Windows, Linux) не используется.
